# Синхронизация данных CRM

## Техническая идея

В исходной реализации покупатели и сделки обрабатываются по одному: для каждой сущности выполняется поиск `AbstractCustomer`, обновление json и сохранение в бд. Таким образом при большом объёме данных это создаёт много запросов к postgresql.

Предложение разделить синхронизацию на **сбор** и **применение**:

1. python получает покупателей и сделки из crm, преобразует их в json-совместимый формат и загружает пакетами (батчами) в staging-таблицы postgresql с одним `run_id`, который присваивается всей синхронизации и используется для всех её пакетов.
2. После успешного завершения сбора postgresql строит временную таблицу соответствий из существующих jsonb-массивов и сопоставляет записи через `JOIN` и `GROUP BY`.
3. Покупатели сопоставляются сначала по crm id, затем по однозначному логину среди сделок. Сделки же - сначала по crm id, затем по однозначному логину среди покупателей.
4. Отсутствующие `AbstractCustomer` создаются пакетно, данные существующих записей обновляются sql-запросами с пересборкой jsonb-массивов по `general.id`.
5. Если сделка по id и покупатель по логину найдены в разных `AbstractCustomer`, через python организуется их объединение с приоритетом записи, найденной по id сделки, после объединения соответствия пересчитываются.
6. Все изменения основной таблицы выполняются в рамках одной транзакции (при ошибке они откатываются). Удаление записей, отсутствующих в CRM, происходит только после успешно завершённой полной выгрузки, частичная синхронизация отсутствующие элементы сохраняет.

`AbstractCustomer` и формат JSONB сохранены, другие части приложения уже работают с этими полями, поэтому изменение структуры потребовало бы переработки остальной логики. В jsonb остаются `general.id`, `general.login`, `general.name` и исходные данные `api_value`,сохраняется возможность существующего поиска по точным логину и названию. А покупатели и сделки связываются через принадлежность одной записи `AbstractCustomer`.

Очистка при успешной полной выгрузке не зависит от названия сущности.

| `crm_sync.py` | Преобразует crm-сущности в json, загружает их пакетами в staging, управляет состоянием выгрузки и вызовом этапа применения. |

## Подключение и запуск

Используется существующие flask-приложение, модель `AbstractCustomer` и клиент `amocrm.py`. Перед запуском необходимо настроить подключение sqlalchemy и postgresql и создать основную таблицу через существующий механизм приложения.

В примерах ниже app - уже настроенный объект flask-приложения из вызывающего проекта. В самом репозитории он не создаётся, поэтому перед использованием примеров необходимо подключить к нему db.

Затем один раз установить вспомогательную sql-схему:

```python
from crm_sync import install_schema
from models import db

with app.app_context():
    install_schema(db.engine)
```

Запуск синхронизации сохраняет прежнюю точку входа:

```python
from main import collect_leads_customers

with app.app_context():
    result = collect_leads_customers(is_full=True)
```

При `is_full=True` после успешного получения всех данных применяется полный снимок и удаляются отсутствующие сущности. 
При `is_full=False` обновляются только пришедшие данные, а отсутствующие сохраняются. Если итератор CRM прерывается с исключением, применение к основной таблице не начинается.

Загрузка во вспомогательные таблицы происходит отдельными транзакциями на каждый пакет. Изменения таблицы `abstract_customer` выполняются в одной транзакции внутри `apply_snapshot()` и откатываются при ошибке.


## Оценка нагрузки

Для **20 000 покупателей и 50 000 сделок** при размере пакета **250** загрузка staging потребует до **80 пакетных `INSERT`** для покупателей и **200** для сделок - это около **280 запросов** суммарно, если все сущности пройдут фильтрацию. 

Дополнительно выполняются запросы управления запусками, массового сопоставления, обновления и очистки. 
Количество запросов увеличивается с числом конфликтных объединений, так как они обрабатываются отдельно.

python обрабатывает данные последовательно и хранит подготовленный пакет размером до 250 записей, а не все 70 000 сущностей одновременно. 
Например, если один объект занимает 2-10 КБ, полезные данные пакета займут примерно **0,5-2,5 МБ** (однако дополнительно расходуется память на объекты python, crm-клиент и временные операции). 
При конфликтном объединении в память загружаются jsonb-данные двух `AbstractCustomer`. При этом основное сопоставление и группировка выполняются на стороне postgresql во временных таблицах.


## Проверки и ограничения

Имеющиеся модульные тесты проверяют преобразование crm-данных, обработку дубликатов в пакете и управление запуском синхронизации с помощью заглушек.
